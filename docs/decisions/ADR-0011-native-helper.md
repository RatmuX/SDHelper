# ADR-0011: Native Windows helper, DPAPI secrets and the test bundle

**Context.** Volume, microphone and media control, and encryption of the TLS key password, need Windows APIs that the JVM cannot reach well (ADR-0001). Phase 3b implements the hybrid design.

**Decisions.**
- **Process and protocol.** `native/windows` is a small Rust program (`sdhelper-native.exe`) that talks JSON-RPC 2.0 on stdio, one JSON object per line; stderr is for logs. It exits when stdin closes, which is how it learns that the agent is gone. Methods are a closed list (`system.version`, `audio.get`, `audio.setVolume`, `audio.setMute`, `media.command`, `media.get`, `dpapi.protect`, `dpapi.unprotect`); parameters are typed and validated (`deny_unknown_fields`), requests over 1 MiB and DPAPI payloads over 64 KiB are refused. Nothing from the phone ever becomes a command line or shell input.
- **Rust structure.** A `Backend` trait separates the protocol from the operating system. `rpc.rs`, the poller and a mock backend are portable and fully unit-tested on any system (13 tests); `win/{audio,media,dpapi}.rs` use the `windows` crate 0.62.2 (MIT OR Apache-2.0). Windows API signatures were read from the crate source rather than recalled, and the Windows code is type-checked and linted for `x86_64-pc-windows-gnu` on Linux; its behaviour is exercised only on Windows (CI and manual).
- **One thread owns the backend.** COM objects belong to the thread that created them, so one thread (multi-threaded apartment) does requests and polling; a second thread only reads stdin.
- **Polling, not events.** Changes made outside SDHelper are noticed by looking every 500 ms (audio) and 1 s (media) and sending `audio.changed` / `media.changed` only when something changed. Event callbacks (`IAudioEndpointVolumeCallback`, SMTC events) would be cheaper and are a later optimisation that does not change the protocol.
- **Audio.** The default render and capture devices are resolved on every call (the default changes when headphones are plugged in). Volume uses the scalar 0..1; mute is per device. Only the default microphone is muted; muting every capture device is not done.
- **Media.** System Media Transport Controls, the same sessions the Windows volume flyout and media keys control. Players that publish no session are invisible; a media-key fallback is a later addition.
- **DPAPI.** `CryptProtectData`/`CryptUnprotectData` with a fixed, non-secret entropy string and `CRYPTPROTECT_UI_FORBIDDEN`. `DpapiSecretStore` keeps ciphertext in `<name>.secret.dpapi`, protects a plain `.secret` from phase 3a in place and removes it (best-effort overwrite first), and **never falls back to a plain file**: without the helper the agent fails loudly. DPAPI protects against other Windows users and against someone reading the disk offline; it does **not** protect against malware running as the same user, which can decrypt too.
- **Helper lifecycle in the agent.** `NativeHelper` starts the process on first use and again after it dies, at most 5 times a minute. A call that had already been sent when the helper died fails and is **not repeated**, because it may have taken effect (a repeated toggle is an undone toggle). A dead helper makes the actions unavailable (`helper.closed`) and the agent keeps restarting it with growing pauses until it answers.
- **Helper location.** `SDHELPER_NATIVE_PATH`, then the folder of the jpackage launcher, the working directory, the developer build output.
- **Test bundle, not a release.** CI builds the helper, runs its tests on real Windows (DPAPI round trip, JSON-RPC), packages the agent with `jpackage --type app-image` (own Java runtime, console enabled) and uploads the folder as a **workflow artifact kept 14 days**. Nothing is published to GitHub Releases. Real releases come with the packaging work of Phase 5.
- **`--demo-platform`.** The same actions on in-memory controllers, to try the phone app without Windows. It is also the test double of the real controllers.

**Alternatives.** JNA/COM from the JVM (hand-written vtables, SMTC unreachable); a local socket instead of stdio (ports, authentication); event callbacks now (more unsafe code, no user-visible gain yet); falling back to plain files when DPAPI is unavailable (silently weakens the one thing DPAPI is for).

**Consequences / not verified.**
- Core Audio, SMTC and DPAPI run for the first time on a real Windows machine through CI and the owner's test; nothing of that could be run on the Linux development machine. The CI machine may have no audio device or player, so those tests accept "no device" answers.
- Volume steps are 5 percentage points; per-application volume, Discord and key injection are later work.
- Polling costs a little CPU while the agent runs, even with no phone connected.
