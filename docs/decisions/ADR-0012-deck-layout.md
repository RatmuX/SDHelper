# ADR-0012: Deck layouts, profiles, presets and the editor

**Context.** Phase 3c turns the plain action list into a paged grid of large square buttons with a separate editing tab, profiles and ready-made layouts. The owner's design: the control panel is landscape; page 1 holds application controls (Discord, OBS and so on), page 2 the system controls; editing is a separate tab with its own edit mode so nobody changes the layout by accident while using the deck; people can have as many pages as they want and edit them by drag and drop; ready-made layouts exist for streaming and gaming.

**Decisions (data model and storage).**
- **Model.** `DeckProfile(grid, pages)`, `DeckPage(slots)`, `DeckSlot.Action(actionId)` in `core:model`, plain Kotlin. All pages of a profile share one grid size (3x2, 4x2 default, 5x2, 4x3, 6x3), so buttons stay the same size when swiping. A profile has 1 to 8 pages; a page has exactly one slot per cell, `null` for an empty cell. The stored form has a slot `type` discriminator, so a later `Folder` slot does not break saved layouts (folders are planned for 3d).
- **Operations are pure functions** (`LayoutOps`): set, clear, move (swap when the target is occupied, also across pages), add/remove/rename/reorder pages, rename, resize. They never throw for bad positions or limits; they return the profile unchanged. **A resize never deletes a button**: buttons keep their row and column where the new grid has that cell, the rest go to free cells of the same page, then other pages, then new pages; if they would not fit in 8 pages the resize is refused. Tested for every pair of allowed grid sizes.
- **Presets** (`LayoutPresets`: Everyday, Streaming, Gaming) are code, not data files, and use only actions that exist today. A test in `data:connection` checks that every action id a preset uses is really published by the built-in providers, so a renamed action fails the build instead of silently breaking the presets. They grow when Discord and OBS actions exist.
- **Storage: one versioned JSON document in Preferences DataStore** (`data:profiles`), not Room. Profiles are small documents edited as a whole; Room would add KSP and schema work for no benefit. This deviates from ADR-0004 on purpose. Reading is forgiving and repairs what it can (unsupported grid to default, slot lists padded or cut to the grid, unknown slot types become empty cells, no pages gives one empty page, too many pages are cut); unreadable data reads as "no profiles", after which the app recreates the Everyday layout. Defaults are written explicitly (a test found that the version number was otherwise omitted).
- **Action catalog cache** (`ActionCatalogCache`): every catalog received from a computer is merged into a persistent cache of id, title, icon and toggle flag. Layouts therefore show titles and icons, and the editor can offer actions, while no computer is connected; buttons are dimmed then. Titles are stored in the language of the moment.
- **Settings** (`data:settings`): haptic feedback and keep-screen-on, both on by default.
- The layouts are stored on the phone, not per computer: they refer to actions by id, and an action a computer does not offer is shown dimmed.

**Alternatives.** Room (see above); a separate layout per computer (duplicates work when the same layout fits all); presets as JSON assets (another format to validate and no compile-time link to action ids).

**Decisions (control panel UI).**
- **Landscape, immersive, large squares.** `ImmersiveLandscape` locks the screen to sensor-landscape while the control panel is shown, hides the system bars (a swipe from the edge shows them briefly), optionally keeps the screen on, and puts everything back on leaving, so all other screens stay portrait. `GridMath` computes the largest equal squares that fit the space (centred, never negative), tested for every grid size on a typical 20:9 landscape phone: the default 4x2 gives buttons larger than 400 px.
- **Pages swipe, nothing moves.** `HorizontalPager` (Compose foundation); every page gets the same space and the profile's grid size, so button size and position are identical on every page. The default Everyday layout follows the owner's design: page 1 application and media controls, page 2 system controls.
- **No editing from the control panel.** The deck screen has no edit affordance at all; editing is a separate tab, and inside it a further "edit mode" switch (see the editor commit).
- **Buttons show meaning, not colors.** An action's `tone` (NORMAL, ACTIVE, WARNING, ALERT) reaches the design module as `DeckTileTone`; Material 3 maps ALERT to the error container (a muted microphone is red), ACTIVE to the primary container. Unavailable buttons are dimmed and ignore taps; offline, layouts still show their titles and icons from the cache.
- **Icons are vector drawables in `ui:design-api`**, converted unchanged from the Apache-2.0 Material icon repository (10 icons, see `docs/THIRD_PARTY.md`), not the 34 MB `material-icons-extended` library. `DeckIconSet` maps the icon key an action carries to a drawable, with two faces for toggle actions (microphone open or crossed, play or pause); unknown keys get a generic icon.
- **`ui:components`** holds what the control panel and the editor share and that is built from the design contract only: grid geometry and hit testing, the grid page, button models, the landscape effect and the drag gestures. Architecture rules: features may use it; it may use only `ui:design-api` and `core:*`.
- **Drag gestures read pointer moves in the `Initial` pass** once a long press has happened. That pass runs from parent to child, so the pager around a page never sees those moves and does not scroll while a button is dragged; before the long press nothing is consumed, so swiping still works.

**Consequences.** Nothing about layouts depends on the network or the agent. The layout and geometry logic is pure and tested; the gesture and drawing code cannot be exercised on the Linux development machine (the emulator does not start) and is verified on the owner's phone.

**Decisions (editor and settings).**
- **Two gates against accidents.** Editing lives on its own home card, away from the control panel, and inside it a further "Edit mode" switch must be on. `EditorViewModel` ignores every change while it is off (tested for each operation), so even a stray touch or a future UI bug cannot alter a layout. Turning it off also drops a pending grid change.
- **Drag and drop on top of tap menus.** A long press lifts a button; the target cell is highlighted, dropping on a filled cell swaps, holding the finger near the left or right edge for 700 ms turns the page (`EdgeDwell`), dropping outside any cell cancels. The pager's own scrolling is disabled while dragging. Every action is also reachable without dragging: tap a cell to choose an action, clear it or "Move to another page", so a gesture problem can never block editing.
- **Edits are serialised and saved at once.** Each change is applied on top of the latest stored layout under a mutex and written immediately; there is no save button and nothing to lose when the app is closed.
- **Grid size changes never delete buttons.** A change that moves nothing is applied directly; one that moves buttons asks first and says how many; one that cannot fit within eight pages is refused with a message.
- **Layouts in the settings.** Choose, add a ready-made one (Everyday, Streaming, Gaming, in the phone's language, never activated automatically), copy, rename, delete with confirmation. The last layout cannot be deleted; copies get unique names within the length limit.
- **Not verified:** the gesture code and the drawing of the drag cannot run on the Linux development machine. The logic behind them (geometry, swap and move, edge dwell, view models) is covered by 280 passing tests in the project; the owner tests the feel on a phone.
